## 1. Введение

### 1.1. Цель

Классифицировать конфиденциальные данные компании «МЕДИКАМЕНТЕ» (выявленные в Задании 1) по состоянию, уровню чувствительности и уровню риска; обосновать выбор способов защиты для каждой категории; составить перечень инструментов и реестр программных и аппаратных средств защиты информации.

### 1.2. Исходные данные

- Список конфиденциальных данных (16 позиций, 4 категории) — Задание 1, раздел 2.
- Матрица «данные → способы защиты» — Задание 1, раздел 6.
- Механизм тегирования `[КАТЕГОРИЯ].[ЧУВСТВИТЕЛЬНОСТЬ].[РЕГУЛЯТОР]` — Задание 1, раздел 7.
- Список инструментов — Задание 1, раздел 8.
- Целевая архитектура (MVP) — Задание 2.

### 1.3. Методология

Классификация выполнена по трём осям:

1. **Состояние данных** (по методологии NIST SP 800-122):
   - **At rest** — данные в состоянии покоя (хранение на дисках, в БД, на носителях);
   - **In transit** — данные при передаче (по сети, между системами);
   - **In processing** — данные при обработке (в оперативной памяти, в интерфейсах, в отчётах).
2. **Уровень чувствительности** — по схеме тегов из Задания 1: `PUBLIC` / `INTERNAL` / `CONFIDENTIAL` / `RESTRICTED`.
3. **Уровень риска** — оценка последствий утечки/искажения: **Высокий** (нарушение законодательства, врачебной тайны, крупный финансовый ущерб), **Средний** (нарушение целостности/доступности, операционные потери), **Низкий** (незначительные последствия).

## 3. Обоснование выбора способов защиты

### 3.1. Шифрование at rest (данные в состоянии покоя)

**Применяется ко всем данным уровня `CONFIDENTIAL` и `RESTRICTED`.**

Обоснование:
- ПЗ-01 (Задание 1): ПДн хранятся в открытом виде на общем диске — прямое нарушение 152-ФЗ и врачебной тайны (323-ФЗ). Шифрование at rest устраняет риск утечки при физическом доступе к носителям и краже оборудования.
- Требования Приказа ФСТЭК России № 21 (меры по обеспечению безопасности ПДн) предусматривают шифрование как базовую меру для специальных категорий.
- Для медицинских данных (п. 7, 8) шифрование обязательно: утечка диагнозов влечёт ответственность по ст. 137 УК РФ (нарушение неприкосновенности частной жизни).

Выбор технологии:
- **Файлы и сканы** — AES-256 (BitLocker, EFS, шифрование объектного хранилища S3/MinIO).
- **Базы данных** — TDE (PostgreSQL, SQL Server) — прозрачное шифрование без изменения приложений.
- **Ключи** — аппаратный HSM или защищённое хранилище ключей (HashiCorp Vault, Azure Key Vault) с регламентом ротации.

### 3.2. Шифрование in transit (данные при передаче)

**Применяется ко всем потокам, содержащим ПДн и финансовые данные.**

Обоснование:
- ПЗ-04 (Задание 1): передача ККМ→1С по TCP/IP-OLE, обмен 1С↔1С по OLE, передача результатов анализов по почте — всё без шифрования и аутентификации. Перехват трафика в локальной сети возможен без специальных средств.
- Требование TLS 1.2+ для всех сетевых обменов, mTLS — для интеграции с лабораторией (взаимная аутентификация сторон), IPSec — для унаследованных протоколов (OLE).

### 3.3. Обфускация (маскирование)

**Применяется к данным, которые отображаются в интерфейсах, но не нужны в полном виде.**

Обоснование:
- Администратору ресепшена для идентификации пациента достаточно части ФИО и последних цифр документа; полные паспортные данные и СНИЛС в интерфейсе не нужны.
- Маскирование снижает риск «заглядывания через плечо» (shoulder surfing) и случайного раскрытия на экранах.
- Неприменимо к медицинским данным (п. 7, 8): врачу нужны полные данные для принятия решений.

### 3.4. Обезличивание (псевдонимизация)

**Применяется к данным, используемым для аналитики, тестирования и отчётности.**

Обоснование:
- ПЗ-13 (Задание 1): аналитика по персональным данным без согласия субъектов — нарушение 152-ФЗ.
- Озеро данных (Задание 2) получает **только обезличенные данные**: прямые идентификаторы (ФИО, телефон, СНИЛС, паспорт) заменяются на псевдоним (PID), соответствие хранится отдельно и защищённо.
- Псевдонимизация сохраняет возможность аналитики (загрузка, повторные визиты) без раскрытия личности.

## 6. Порядок внедрения

1. **Этап 1 (0–3 мес.). Базовые меры:** шифрование дисков (BitLocker), переход 1С на клиент-серверный режим с TDE, разграничение доступа (ACL), внедрение MFA (Keycloak), настройка резервного копирования и антивируса.
2. **Этап 2 (3–9 мес.). Целевая архитектура:** развёртывание МИС (Задание 2), объектное хранилище с шифрованием, SIEM/EDR (Wazuh), DLP и тегирование (Microsoft Purview), защищённая интеграция с лабораторией (mTLS).
3. **Этап 3 (9–18 мес.). Аналитический контур:** озеро данных с обезличенными данными (ARX/Amnesia, Apache Atlas), аппаратное хранение ключей (HSM), физическая безопасность (СКУД, ИБП).

Каждый этап завершается проверкой: соответствие классификации (раздел 2), актуализация реестра (раздел 5), аудит внедрённых мер.
