# Задание 2. Проектирование целевой архитектуры (MVP)

## 1. Введение

Цель задания — спроектировать целевую архитектуру информационной системы компании «Медикаменте» на основе результатов анализа безопасности (Задание 1) и требований технического задания.

Формат проектирования выбран: **«Контекст + контейнеры»** (уровни C4-модели). На уровне контекста показана система в целом и её взаимодействие с внешними системами и пользователями; на уровне контейнеров — технологические компоненты, из которых состоит медицинская информационная система (МИС), и связи между ними.

Целевая архитектура описывает **минимально жизнеспособный продукт (MVP)** — первый этап внедрения, который закрывает критичные проблемные зоны, выявленные в Задании 1, и создаёт фундамент для дальнейшего развития (рост в 5 раз, филиалы, мобильное приложение, интеграция с лабораторией, озеро данных для BI/ML/AI).

## 2. Целевая архитектура (уровень контекста)

Диаграмма: `C4_Context_ToBe.drawio.xml`.

### 2.1. Границы системы

Целевая система **«МЕДИКАМЕНТЕ — Целевое состояние (MVP)»** включает:

- **МИС** (медицинская информационная система) — ядро, заменяющее ручной учёт;
- **Портал клиентов** — запись на приём, оплата, просмотр результатов;
- **Мобильное приложение** — запись, результаты, уведомления;
- **Портал ресепшена** — АРМ администратора (регистрация, запись, оплата);
- **CRM** — клиентская база и коммуникации;
- **Платёжный шлюз** — онлайн-оплата;
- **Озеро данных** — аналитический слой для BI/ML/AI;
- **IAM/Keycloak** — централизованная аутентификация и управление доступом.

### 2.2. Внешние системы и пользователи

| Элемент | Тип | Взаимодействие |
|---|---|---|
| Пациент | Внешний пользователь | Запись, оплата, результаты через портал/приложение |
| Администратор | Внутренний пользователь | Работа через портал ресепшена |
| Доктор | Внутренний пользователь | Ведение медкарт, назначение анализов |
| Кассир | Внутренний пользователь | Приём оплаты, работа с ККМ |
| Бухгалтер | Внутренний пользователь | Учёт в 1С:Бухгалтерия |
| Сотрудник склада | Внутренний пользователь | Учёт ТМЦ в 1С:Торговля и склад |
| Лаборатория | Внешняя система | Заказы и результаты анализов по API (mTLS) |
| Банк (эквайер) | Внешняя система | Платёжные операции |
| 1С:Бухгалтерия | Внешняя система | Бухгалтерский учёт (клиент-сервер, TDE) |
| 1С:Торговля и склад | Внешняя система | Учёт ТМЦ (клиент-сервер, TDE) |
| ККМ | Внешняя система | Фискализация платежей |
| Exchange | Внешняя система | Корпоративная почта |

### 2.3. Ключевые решения уровня контекста

1. **Вынос 1С в клиент-серверный режим** — устраняет проблему файлового режима (ПЗ-06, ПЗ-07 из Задания 1): блокировки, отсутствие аудита, риск потери целостности.
2. **Единая точка входа через API Gateway** — все клиентские приложения работают через один защищённый шлюз (TLS, rate limiting, централизованный аудит).
3. **Централизованная идентификация (IAM/Keycloak)** — OIDC, RBAC, MFA; устраняет разрозненные учётные записи и общие пароли (ПЗ-03, ПЗ-04).
4. **Интеграция с лабораторией по API (mTLS)** — заменяет передачу результатов по электронной почте и бумаге (ПЗ-10).
5. **Озеро данных** — аналитический слой, куда попадают **только обезличенные** данные (см. раздел 5).

## 3. Целевая архитектура (уровень контейнеров)

Диаграмма: `C4_Containers_ToBe.drawio.xml`.

### 3.1. Состав контейнеров МИС

| Контейнер | Тип | Назначение | Технологии |
|---|---|---|---|
| Портал клиентов | Web Application | Запись, оплата, результаты | React SPA |
| Мобильное приложение | Mobile App | Запись, результаты, уведомления | React Native |
| Портал ресепшена | Web Application | АРМ администратора | React SPA |
| API Gateway | Container | Маршрутизация, TLS, rate limiting | NGINX/Kong |
| Patient Service | Container | Реестр пациентов | Java 21 / Spring Boot |
| Appointment Service | Container | Записи к специалистам | Java 21 / Spring Boot |
| Medical Records Service | Container | Медкарты, сканы документов | Java 21 / Spring Boot |
| Payment Service | Container | Платежи, интеграция с шлюзом | Java 21 / Spring Boot |
| Lab Integration Service | Container | API лаборатории | Java 21 / Spring Boot |
| Analytics Service | Container | Обезличивание, выгрузка в Data Lake | Java 21 / Spring Boot |
| PostgreSQL | Database | Основная БД (TDE, RBAC, аудит) | PostgreSQL |
| Redis | Container | Кэш, сессии | Redis |
| Object Storage | Container | Сканы медкарт (AES-256) | S3/MinIO |
| Kafka | Container | Шина событий (TLS) | Apache Kafka |
| Data Lake | Database | Обезличенные данные для BI/ML/AI | ClickHouse |
| IAM / Keycloak | Container | OIDC, RBAC, MFA | Keycloak |

### 3.2. Ключевые решения уровня контейнеров

1. **Микросервисная архитектура с выделенными сервисами по доменам** (пациенты, записи, медкарты, платежи, лаборатория, аналитика). Обеспечивает масштабируемость (рост в 5 раз), независимое развёртывание и сопровождаемость.
2. **Java 21 / Spring Boot** — современный стек, поддержка виртуальных потоков для высоконагруженных операций записи и оплаты.
3. **PostgreSQL с TDE и аудитом** — единое хранилище операционных данных; шифрование на уровне хранения закрывает ПЗ-01 (данные на диске без шифрования).
4. **Object Storage (S3/MinIO) с AES-256** — сканы медкарт и документов вынесены из файлового сервера (ПЗ-02: общий диск без разграничения доступа).
5. **Kafka как шина событий** — асинхронная передача событий между сервисами и в аналитический слой; события в Data Lake передаются **только в обезличенном виде**.
6. **Keycloak (OIDC)** — единая аутентификация для всех приложений, ролевая модель (RBAC), поддержка MFA для администраторов и врачей.
7. **Интеграции защищены по уровням**: mTLS — с лабораторией, TLS 1.2+ — с платёжным шлюзом и 1С, TLS/IPSec — с ККМ.

## 4. Принципы Privacy by Design

Архитектура спроектирована с учётом принципов Privacy by Design (встроенная конфиденциальность):

| Принцип | Реализация в архитектуре |
|---|---|
| Проактивность, а не реактивность | Защита закладывается на этапе проектирования, а не добавляется после инцидента |
| Конфиденциальность по умолчанию | Доступ к ПДн только по ролям (RBAC); пациент видит только свои данные |
| Встроенная защита | Шифрование на всех уровнях: at rest (TDE, AES-256), in transit (TLS 1.2+, mTLS) |
| Полная функциональность | Защита не снижает функциональность: сервисы разделены, но работают как единая система |
| Сквозная защита жизненного цикла | Аудит всех операций с ПДн, журналирование в IAM и БД |
| Прозрачность | Пациент видит свои данные и историю операций через портал |
| Уважение к приватности пользователя | Минимизация данных: собираются только данные, необходимые для оказания услуг |

### 4.1. Минимизация данных

- В портале клиентов и мобильном приложении собираются только данные, необходимые для записи и оплаты (ФИО, контакты, дата рождения).
- Медицинские данные (диагнозы, результаты анализов) не передаются в CRM и платёжный шлюз.
- В аналитический слой попадают только обезличенные данные (см. раздел 5).

### 4.2. Разграничение доступа (RBAC)

| Роль | Доступ |
|---|---|
| Пациент | Свои записи, свои результаты, оплата |
| Администратор | Регистрация, запись, оплата (без медданных) |
| Доктор | Медкарты своих пациентов |
| Кассир | Оплата, ККМ (без медданных) |
| Бухгалтер | Финансовые данные (без медданных) |
| Сотрудник склада | ТМЦ (без ПДн) |
| Аналитик | Только обезличенные данные из Data Lake |

## 5. Аналитический слой (озеро данных)

### 5.1. Назначение

Озеро данных (Data Lake на ClickHouse) — аналитический слой для BI-отчётности, ML-моделей и AI-сервисов. Создаётся в рамках MVP как фундамент для стратегических целей компании.

### 5.2. Принцип работы

1. Сервисы МИС публикуют события в Kafka.
2. **Analytics Service** выполняет обезличивание (псевдонимизацию) данных: замена прямых идентификаторов (ФИО, телефон, СНИЛС) на псевдонимы, агрегация, удаление прямых идентификаторов.
3. В Data Lake загружаются **только обезличенные данные** — это исключает утечку ПДн через аналитический контур (ПЗ-13 из Задания 1: аналитика по персональным данным без согласия).

### 5.3. Состав данных

- Загрузка по специалистам и времени (агрегированная);
- Структура услуг и выручка (без привязки к пациентам);
- Загрузка лаборатории (агрегированная, без идентификации);
- Оборачиваемость ТМЦ;
- Метрики качества обслуживания (время ожидания, отмены).

### 5.4. Защита аналитического контура

- Доступ к Data Lake — только для аналитиков (роль «Аналитик»);
- Данные в Data Lake не содержат прямых идентификаторов;
- Соединения с Data Lake — по TLS;
- Разделение контуров: операционный контур (МИС) и аналитический контур (Data Lake) изолированы, обмен только через Analytics Service.

## 6. Соответствие нефункциональным требованиям (НФТ)

| НФТ | Реализация |
|---|---|
| **Конфиденциальность** | TDE/AES-256 at rest, TLS 1.2+/mTLS in transit, RBAC, аудит, обезличивание в аналитике, Privacy by Design |
| **Масштабируемость** | Микросервисы + Kafka + горизонтальное масштабирование PostgreSQL/ClickHouse; рост в 5 раз без перепроектирования |
| **Сопровождаемость** | Модульная архитектура, единый стек Java 21/Spring Boot, централизованный IAM, документированные API |
| **Конфигурируемость** | Параметры записи, расписания, тарифы и роли настраиваются через конфигурацию, без изменения кода |

## 7. Связь с Заданием 1

Целевая архитектура закрывает проблемные зоны, выявленные в Задании 1:

| Проблемная зона (Задание 1) | Решение в целевой архитектуре |
|---|---|
| ПЗ-01: данные на диске без шифрования | TDE в PostgreSQL, AES-256 в Object Storage |
| ПЗ-02: общий диск без разграничения доступа | Object Storage + RBAC, файловый сервер выводится из контура ПДн |
| ПЗ-03, ПЗ-04: общие пароли, нет MFA | Keycloak: OIDC, RBAC, MFA |
| ПЗ-06, ПЗ-07: файловый режим 1С | 1С в клиент-серверном режиме, TDE |
| ПЗ-10: передача результатов анализов по почте | Lab Integration Service по mTLS |
| ПЗ-13: аналитика по ПДн без согласия | Обезличивание в Analytics Service, изоляция Data Lake |
| ПЗ-15: отсутствие аудита операций | Журналирование в БД и IAM, централизованный аудит |

## 8. Этапы внедрения (MVP)

1. **Этап 1. Фундамент**: развёртывание PostgreSQL (TDE), Keycloak, API Gateway, перенос 1С в клиент-серверный режим.
2. **Этап 2. Ядро МИС**: Patient Service, Appointment Service, Medical Records Service, портал ресепшена.
3. **Этап 3. Клиентские сервисы**: портал клиентов, мобильное приложение, Payment Service + платёжный шлюз.
4. **Этап 4. Интеграции**: Lab Integration Service (mTLS), интеграция с ККМ и 1С.
5. **Этап 5. Аналитика**: Kafka, Analytics Service, Data Lake (ClickHouse), BI-отчёты.

Каждый этап завершается проверкой на соответствие НФТ и требованиям законодательства (152-ФЗ, 323-ФЗ, 54-ФЗ).
