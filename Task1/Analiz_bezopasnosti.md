## 1. Введение

### 1.1. Цель

Провести анализ безопасности информационной системы медицинского центра «МЕДИКАМЕНТЕ» в текущем состоянии (As-Is): выявить конфиденциальные данные, построить карту потоков данных (DFD), провести аудит мер безопасности, составить список проблемных зон и предложить меры защиты с отражением их на доработанных диаграммах (To-Be).

### 1.2. Исходные данные

- C4-диаграмма текущего состояния (As-Is), предоставленная заказчиком: `As-Is_C4_original.drawio.xml`.
- Описание компании: 1 офис, 20 административных и 15 медицинских сотрудников; учёт ведётся вручную (Excel, сканы, JPG/PDF на общем файловом сервере); используются 1С:Бухгалтерия предприятия и 1С:Торговля и склад (обе — в файловом режиме), контрольно-кассовая машина (ККМ) с подключением по TCP/IP-OLE; Windows Server 2022 (AD, DNS, DHCP, LDAP, файловый сервер, Exchange).
- Планы развития: рост в 5 раз, открытие новых филиалов, мобильное приложение, интеграция с лабораторией по API, озеро данных для BI/ML/AI, внедрение новых систем (портал клиентов, портал ресепшена, платёжный шлюз, CRM, лаборатория).
- Нефункциональные требования: конфиденциальность, масштабируемость, сопровождаемость, конфигурируемость.
- Законодательство: Федеральный закон № 152-ФЗ «О персональных данных», требования к медицинской тайне (ФЗ-323 «Об основах охраны здоровья граждан»).

### 1.3. Методология

- Нотация DFD — **Gane-Sarson** (внешние сущности — прямоугольники, процессы — скруглённые прямоугольники, хранилища данных — открытые прямоугольники, потоки — стрелки с подписями).
- Уровни: **Level 0** (контекстная диаграмма) и **Level 1** (декомпозиция по процессам).
- Потоки, содержащие персональные данные (ПДн), на диаграммах выделены **красным цветом** и помечены меткой `[ПДн]`.
- Подход: сначала As-Is (фактическое состояние), затем аудит, затем To-Be (доработанные диаграммы с мерами защиты на каждом этапе потока).

## 3. DFD-диаграммы потоков данных

Диаграммы построены в нотации Gane-Sarson и сохранены в файле **`DFD_AsIs.drawio.xml`** (7 страниц):

| Страница | Содержание |
|----------|------------|
| Level 0 — Контекст (As-Is) | Контекстная диаграмма всей системы: внешние сущности (Пациент, Администратор, Доктор, Кассир, Бухгалтер, Сотрудник склада, Лаборатория, Exchange) и единый процесс «Медицинский центр МЕДИКАМЕНТЕ» |
| P1 — Запись к специалисту (As-Is) | Процессы 1.1 «Приём записи», 1.2 «Регистрация записи в журнале»; хранилище D1 `Journal-Doctor-FIO.xlsx` |
| P2 — Регистрация пациента (As-Is) | Процессы 2.1 «Регистрация в реестре», 2.2 «Ведение файла пациента»; хранилища D2 `Patients.xlsx`, D3 `Data file` |
| P3 — Приём оплаты (As-Is) | Процессы 3.1 «Приём оплаты», 3.2 «Фискализация чека (ККМ)», 3.3 «Передача в 1С:Бухгалтерию»; хранилища D4 ККМ, D5 1С:Бухгалтерия |
| P4 — Учёт анализов (As-Is) | Процессы 4.1 «Приём результатов», 4.2 «Формирование реестра за день»; хранилище D6 `RegistryByDate.xlsx` |
| P5 — Учёт ТМЦ (As-Is) | Процессы 5.1 «Приём/списание ТМЦ», 5.2 «Учёт в 1С:Торговля и склад», 5.3 «Обмен с 1С:Бухгалтерией (OLE)»; хранилища D7 1С:Торговля, D5 1С:Бухгалтерия |
| P6 — Бухгалтерский учёт (As-Is) | Процессы 6.1 «Ввод учётных данных», 6.2 «Формирование отчётности»; хранилище D5 1С:Бухгалтерия |

**Ключевые наблюдения по диаграммам:**

1. **Все потоки с ПДн (красные) идут в открытом виде** — без шифрования, без контроля доступа на уровне файлов.
2. **Хранилища D1–D3, D6 — это Excel-файлы и произвольные файлы на общем диске** (файловый сервер Windows). Доступ к ним не разграничен: любой сотрудник с учётной записью в домене может открыть файлы.
3. **Лаборатория** на контекстной диаграмме — внешняя сущность, обмен результатами анализов происходит на бумажном носителе или файлами без защищённого канала.
4. **ККМ → 1С:Бухгалтерия** — передача по TCP/IP-OLE без шифрования и аутентификации.
5. **1С:Бухгалтерия ↔ 1С:Торговля** — обмен по OLE внутри платформы, без контроля целостности.
6. **Exchange** используется для внутренней почты; передача отчётности по почте не контролируется (нет DLP, нет шифрования вложений).

## 4. Аудит мер безопасности

Аудит проведён по направлениям: организационные меры, технические меры, физическая безопасность, соответствие требованиям законодательства.

### 4.1. Организационные меры

| Мера | Статус | Комментарий |
|------|--------|-------------|
| Политика обработки ПДн | ❌ Отсутствует | Нет утверждённого документа, нет назначенного ответственного за обработку ПДн |
| Согласие на обработку ПДн | ❌ Не подтверждено | Нет данных о получении согласий пациентов |
| Инструктаж сотрудников по работе с ПДн | ❌ Отсутствует | Сотрудники не обучены |
| Разграничение ролей и ответственности | ❌ Отсутствует | Все сотрудники имеют одинаковый доступ к файловому серверу |
| Журнал учёта обращений к ПДн | ❌ Отсутствует | Нет регистрации фактов доступа |

### 4.2. Технические меры

| Мера | Статус | Комментарий |
|------|--------|-------------|
| Разграничение доступа к файлам (ACL) | ❌ Отсутствует | Общий диск доступен всем доменным пользователям |
| Аутентификация | ⚠️ Частично | Есть AD/LDAP, но учётные записи общие, пароли не ротируются, нет MFA |
| Шифрование данных at rest | ❌ Отсутствует | Excel-файлы и сканы хранятся в открытом виде |
| Шифрование данных in transit | ❌ Отсутствует | OLE/TCP/IP-обмен ККМ↔1С, файловые обмены без TLS |
| Аудит и журналирование доступа | ❌ Отсутствует | Нет журналов доступа к файлам, нет SIEM |
| Антивирусная защита | ⚠️ Не подтверждена | Нет данных о наличии и обновлении антивируса |
| Резервное копирование | ⚠️ Не подтверждено | Нет данных о регламенте бэкапов |
| Контроль целостности | ❌ Отсутствует | Нет ЭЦП, нет контроля изменений файлов |
| DLP-система | ❌ Отсутствует | Передача ПДн по почте/на носителях не контролируется |

### 4.3. Физическая безопасность

| Мера | Статус | Комментарий |
|------|--------|-------------|
| Контроль доступа в помещения | ⚠️ Не подтверждён | Нет данных о СКУД |
| Защита серверной | ⚠️ Не подтверждена | Нет данных |
| Уничтожение бумажных носителей с ПДн | ❌ Не подтверждено | Сканы и бумажные карты хранятся без регламента уничтожения |

### 4.4. Соответствие законодательству

| Требование | Статус | Комментарий |
|------------|--------|-------------|
| 152-ФЗ: уведомление Роскомнадзора об обработке ПДн | ❌ Не подтверждено | Нет данных |

## 5. Список проблемных зон

Проблемные зоны пронумерованы (ПЗ-01 … ПЗ-15) и сгруппированы по критичности. Критичность: **Высокая** — прямое нарушение законодательства или высокий риск утечки ПДн; **Средняя** — риск нарушения целостности/доступности; **Низкая** — операционные неудобства.

### 5.1. Высокая критичность

| № | Проблемная зона | Описание | Риск |
|---|-----------------|----------|------|
| ПЗ-01 | **Хранение ПДн в открытом виде на общем диске** | Excel-файлы (`Patients.xlsx`, `Journal-Doctor-FIO.xlsx`, `RegistryByDate.xlsx`) и сканы медкарт (`Data file`) лежат в открытом виде на файловом сервере без шифрования и разграничения доступа | Утечка ПДн, нарушение 152-ФЗ, врачебной тайны |
| ПЗ-02 | **Отсутствие разграничения доступа (ACL)** | Любой доменный пользователь может открыть любую папку/файл | Несанкционированный доступ к ПДн |
| ПЗ-03 | **Отсутствие аудита доступа** | Нет журналов: кто, когда и к каким файлам обращался | Невозможность расследования инцидентов |
| ПЗ-04 | **Передача ПДн по незащищённым каналам** | ККМ→1С (TCP/IP-OLE), 1С↔1С (OLE), обмен с лабораторией (бумага/файлы) — без шифрования и аутентификации | Перехват ПДн |
| ПЗ-05 | **Отсутствие согласий и политики ПДн** | Нет документов, регламентирующих обработку ПДн | Нарушение 152-ФЗ, штрафы |
| ПЗ-06 | **Общие учётные записи, слабая аутентификация** | Нет MFA, пароли не ротируются, возможно использование общих учёток | Компрометация учётных записей |
| ПЗ-07 | **Медицинская тайна не защищена технически** | Диагнозы, назначения, результаты анализов доступны администраторам ресепшена | Нарушение 323-ФЗ |

### 5.2. Средняя критичность

| № | Проблемная зона | Описание | Риск |
|---|-----------------|----------|------|
| ПЗ-08 | **Файловый режим 1С** | 1С:Бухгалтерия и 1С:Торговля работают в файловом режиме — база представляет собой файл на диске, доступный всем | Повреждение/кража базы |
| ПЗ-09 | **Отсутствие резервного копирования** | Нет регламента бэкапов, нет проверки восстановления | Потеря данных |
| ПЗ-10 | **Отсутствие контроля целостности** | Файлы можно незаметно изменить; нет ЭЦП, нет хеширования | Фальсификация данных |
| ПЗ-11 | **Отсутствие DLP** | ПДн могут уходить по почте (Exchange), на флешках, в мессенджерах без контроля | Утечка ПДн |
| ПЗ-12 | **Нет антивирусной защиты (не подтверждена)** | Файловый сервер и рабочие станции | Заражение, шифровальщики |

### 5.3. Низкая критичность

| № | Проблемная зона | Описание | Риск |
|---|-----------------|----------|------|
| ПЗ-13 | **Ручной ввод данных** | Двойной ввод (журнал + реестр + 1С), ошибки операторов | Ошибки в данных |
| ПЗ-14 | **Дублирование данных** | Один пациент — несколько файлов/записей в разных местах | Рассинхронизация |
| ПЗ-15 | **Отсутствие регламента уничтожения** | Бумажные носители и старые файлы с ПДн не уничтожаются по регламенту | Накопление ПДн |

| 15 | Учёт ТМЦ | ✅ AES-256 | ✅ TLS 1.2+ | ❌ | ❌ |
| 16 | Бухгалтерская отчётность | ✅ AES-256 | ✅ TLS 1.2+ | ❌ | ❌ |

### 6.2. Пояснения к способам защиты

**Шифрование at rest (данные в состоянии покоя):**
- Файлы Excel и сканы медкарт — шифрование на уровне файлов (AES-256) или перенос в СУБД с шифрованием (TDE).
- Базы 1С — переход с файлового режима на клиент-серверный (SQL Server) с шифрованием.
- Ключи шифрования — в аппаратном HSM или в защищённом хранилище ключей (Azure Key Vault / AWS KMS / локальный HSM), ротация ключей по регламенту.

**Шифрование in transit (данные при передаче):**
- Все сетевые обмены — TLS 1.2+ (HTTPS, LDAPS, SMB 3.0 с шифрованием, IPSec для OLE-обмена ККМ↔1С).
- Обмен с лабораторией — защищённый API (HTTPS + mTLS) вместо бумаги/файлов.
- Почта — шифрование вложений (S/MIME) или DLP-контроль.

**Обфускация (маскирование):**
- В интерфейсах ресепшена ФИО/паспорт/СНИЛС показываются частично (например, `Ива*** Иван И.**`).
- В отчётах и журналах — маскирование чувствительных полей.

**Обезличивание (для аналитики и тестирования):**
- Псевдонимизация: замена ФИО и документов на уникальный идентификатор пациента (PID) с хранением соответствия отдельно и защищённо.
- Для озера данных (BI/ML/AI) — только обезличенные данные (агрегаты, псевдонимы).
- Анонимизация: удаление прямых и косвенных идентификаторов для статистических выборок.

## 7. Механизм тегирования данных

Тегирование (data tagging) — присвоение каждому элементу данных метки, описывающей его чувствительность и правила обработки. Механизм позволяет автоматизировать контроль: DLP, шифрование, доступ, аудит.

### 7.1. Схема тегов

Каждый тег имеет формат: `[КАТЕГОРИЯ].[ЧУВСТВИТЕЛЬНОСТЬ].[РЕГУЛЯТОР]`

| Компонент | Значения | Описание |
|-----------|----------|----------|
| КАТЕГОРИЯ | `PATIENT` / `EMPLOYEE` / `FINANCE` / `MEDICAL` / `INVENTORY` / `ACCOUNTING` | К какой категории относится |
| ЧУВСТВИТЕЛЬНОСТЬ | `PUBLIC` / `INTERNAL` / `CONFIDENTIAL` / `RESTRICTED` | Уровень чувствительности |
| РЕГУЛЯТОР | `152-FZ` / `323-FZ` / `54-FZ` / `98-FZ` / `NONE` | Применимый закон |

### 7.2. Примеры тегов

| Данные | Тег |
|--------|-----|
| ФИО пациента | `PATIENT.CONFIDENTIAL.152-FZ` |
| Диагноз, назначения | `MEDICAL.RESTRICTED.323-FZ` |
| Результаты анализов | `MEDICAL.RESTRICTED.323-FZ` |
| Паспортные данные | `PATIENT.RESTRICTED.152-FZ` |
| Зарплата | `EMPLOYEE.RESTRICTED.152-FZ` |
| Платёжные данные | `FINANCE.CONFIDENTIAL.54-FZ` |
| Учёт ТМЦ | `INVENTORY.INTERNAL.NONE` |
| Бухгалтерская отчётность | `ACCOUNTING.CONFIDENTIAL.98-FZ` |

### 7.3. Правила обработки по тегам

| Чувствительность | Шифрование at rest | Шифрование in transit | Доступ | Аудит | Обезличивание для аналитики |
|------------------|:---:|:---:|:---:|:---:|:---:|
| `PUBLIC` | ❌ | ❌ | Все | ❌ | ❌ |
| `INTERNAL` | ✅ | ✅ | Сотрудники | ⚠️ | ❌ |
| `CONFIDENTIAL` | ✅ AES-256 | ✅ TLS 1.2+ | По ролям (RBAC) | ✅ | ✅ |
| `RESTRICTED` | ✅ AES-256 | ✅ TLS 1.2+ | Минимум ролей, обоснование доступа | ✅ (обязательно) | ✅ (только псевдоним) |

### 7.4. Внедрение тегирования

1. **Каталог данных (data catalog):** завести реестр всех хранилищ и полей с тегами (инструмент: Apache Atlas, Collibra, OpenMetadata).
2. **Тегирование на уровне файлов:** для файлового сервера — расширенные атрибуты NTFS + классификация (Microsoft Purview Information Protection / Azure Information Protection).
3. **Тегирование в БД:** метаданные колонок в СУБД (SQL Server Extended Properties, PostgreSQL COMMENT).
4. **Автоматический контроль:** DLP-система и SIEM используют теги для правил (блокировка отправки `RESTRICTED` по почте, алерты на доступ к `RESTRICTED`).
5. **Проверка:** регулярный аудит соответствия тегов фактическим данным.
